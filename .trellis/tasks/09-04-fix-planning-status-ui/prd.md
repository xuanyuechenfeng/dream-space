# 修复规划合同失败并优化生成进行中展示

## Goal

修复集合规划模型返回合法 JSON 但槽位 `prompt.modelInput` 合同校验失败导致的规划失败，并让用户在点击提交后立即看到明确的生成进行中状态，而不是长时间停留在“等待规划”后才收到超时提示。

## Confirmed Facts

- 附件日志显示模型请求耗时约 114 秒，返回长度 5609 的对象；失败点是
  `ChatPlanningModel.requireCollectionContract` 第 258-262 行，具体错误为
  `collection planning model returned invalid prompt modelInput`。因此首要问题是嵌套字段类型/缺失兼容性，不是 JSON 语法错误。
- Worker 对规划失败使用队列投递重试；最终失败前，API 已创建的是异步 preflight 而不是正式生成任务。
- 前端 `generation.submit` 当前等待 `preflight` READY 后才调用 `createFromPreflight`，所以正式任务卡片不会在点击后立即出现；`waitForPreflight` 使用 120 秒超时，造成用户看到“等待规划”数分钟后才报错。
- 项目已有多图槽位状态、SSE、继续缺失和全部重新生成基础实现；本任务应在既有改动上补缺，不回滚或覆盖工作区其他未提交变更。

## Requirements

### R1. 规划合同兼容与错误传播

1. 规划响应仅严格校验执行链路需要的必要字段及内容完整性；`prompt.modelInput` 等辅助字段缺失、为 `null` 或类型异常时使用安全默认值，未知字段直接忽略，不得因此判定规划失败。
2. 规划失败必须在 preflight 终态中写入稳定错误码和用户可理解的详情，通过 preflight SSE/查询及时返回；不得把业务失败伪装为前端网络超时。
3. 规划重试次数和单次等待时间必须可配置或至少可观测，日志须包含耗时、响应长度、顶层形状和截断预览，不包含完整 prompt、凭据或 planToken。

### R2. 提交后的即时前台反馈

1. 用户点击提交并通过本地校验后，前端立即在当前会话中展示一个稳定尺寸的“生成进行中”临时项，状态语义为“正在准备生成/生成中”，不得显示为“等待规划”。
2. 进行中状态出现时立即清空底部输入框，已提交描述由进行中卡片承载；失败后的重试或再次编辑仍可从提交快照恢复原描述。
3. 临时项必须显示原始描述、输出规格、目标数量（自动模式可先显示“数量解析中”）和进度占位；不得提前展示已扣费或已消费额度，也不得向用户暴露“临时项”“不计费”“预规划”等内部实现语义。
4. preflight READY 后，临时项原位替换为正式任务及其固定槽位；规划失败、需要澄清、过期或超时后，临时项原位转为明确错误态，提供重试/修改描述入口，不残留无限 loading。
5. 正式任务创建后继续使用现有 SSE 和槽位状态展示：完成数/目标数、实际消费、部分失败、取消、继续缺失和全部重新生成均保持可见且不跳位。
6. 单图与多图均遵循同一交互协议；桌面和移动端不得横向溢出、重叠或因占位替换产生明显布局跳动。

### R3. 回归与安全

1. 规划合同、preflight 状态传播、前端 store 状态转换和页面关键状态均有自动化测试。
2. 现有幂等、额度、任务和槽位状态不变量不得回归；规划失败不得创建正式任务或产生额度流水。

## Acceptance Criteria

- [x] AC1: 附件所示缺失、空值或非对象 `modelInput` 均归一化为空对象，不再导致规划失败；缺失必要字段或必要内容不完整仍以明确合同错误终止并可观测。
- [x] AC2: 合法规划 READY、需要澄清、失败和过期均能在前端显示对应终态；客户端不因等待时间过长主动中断，最终状态以服务端为准。
- [x] AC3: 点击提交后 1 个前端渲染周期内出现“进行中”临时项；READY 后原位替换正式任务，失败后可重试或修改。
- [x] AC4: 正式任务创建前不预留/消费额度；规划失败不创建正式任务。
- [x] AC5: 现有单图、多图槽位增量展示、SSE 重连、取消、继续缺失和全部重新生成测试通过。
- [x] AC6: 桌面与移动视口无横向溢出、文本重叠或明显布局跳动；构建与相关单元测试通过。

## Design Decision

保留后端“preflight 失败不创建正式任务”的账务边界，在前端增加仅用于承载提交状态、可被正式任务替换的内部项。用户界面只展示自然的“正在准备生成/生成中”状态，不显示“不计费”“临时项”或“预规划”等内部实现语义。正式任务创建前不展示消费额度；规划失败后原位显示明确错误和可操作入口。

## Out Of Scope

- 不扩大单任务图片数量上限，不支持槽位级规格或价格差异。
- 不重写现有多图账务模型，不修改已执行数据库迁移。
- 不把前端临时项当作可查询的正式任务或计费事实。
